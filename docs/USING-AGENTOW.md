# How to use agentOW

agentOW is an automation harness for odsp-web development. Starting from a requirement, it researches the codebase, plans, implements, builds, tests, validates the page, reviews the code, and finally opens a draft PR.

What agentOW is not is a substitute for requirements and project knowledge. To use Auto or Batch mode reliably, the order that works is:

```text
Project context (source of truth)
        ↓
Cross-session memory (always reads the context first)
        ↓
agentOW (executes, verifies, and delivers)
```

## 1. Why this has to be spec-driven

When a requirement is incomplete, a person asks a question, looks something up, or falls back on unwritten experience. A zero-interaction agent cannot pause mid-run to collect any of that. It can only make assumptions from whatever context it could read at startup.

That makes **sufficient, accurate, locatable context a precondition for running the harness without interaction**. The shorter the prompt, the more the agent leans on long-lived context. Running Auto or Batch with no source of truth typically produces:

- a correct implementation of the wrong requirement;
- duplicated work that somebody else already finished;
- code built on outdated architecture or design;
- no way to tell what state the UI is supposed to be in;
- an unauditable guess between several reasonable options.

Spec-driven does not mean writing one enormous, perfect spec up front. It means project facts have a definite home, tasks have verifiable success criteria, and the agent knows what to believe when sources disagree.

## 2. Build the project context

Give the project a long-lived context that people and agents share as the source of truth. It can live in:

- a private GitHub repository — best for work spanning teams and codebases;
- the odsp-web repository — best when it should be versioned alongside the code;
- an existing team documentation repository — fine as long as every execution environment can reach it.

Do not chase completeness on day one. Have an AI read the relevant code and summarize the structure, then have someone who knows the project correct it. A practical starting layout:

```text
project-context/
├── README.md              # entry point, reading order, document index
├── architecture.md        # code structure, component boundaries, data flow
├── product-spec.md        # user problems, requirements, acceptance criteria
├── engineering-design.md  # technical approach, constraints, compatibility
├── design.md              # Figma, screenshots, visual states, interactions
├── decisions.md           # confirmed decisions and the reasoning behind them
├── terminology.md         # business and code vocabulary
├── status.md              # current progress, owners, completed work
├── work-items.md          # ADO queries, area paths, task tracking entry points
└── lessons.md             # problems and lessons found in real runs
```

`README.md` should be the stable entry point. It states:

1. what problem this project solves;
2. which files must be read first;
3. which file answers which kind of question;
4. the precedence order when information conflicts;
5. where the current state lives, and which ADO query or work item to follow.

### What belongs in the context

- an architecture overview generated by AI from the code and corrected by a human;
- PM specs, user scenarios, and acceptance criteria;
- developer design, API contracts, data flow, and dependencies;
- Figma links, exports, key page screenshots, and interaction states;
- confirmed technical decisions, constraints, and explicit non-goals;
- related PRs, work items, experiment results, and historical background;
- work that teammates have finished or have in flight;
- queries and filter rules for ADO bug lists and TODO work items;
- wrong assumptions and new knowledge that agentOW runs expose.

Task titles, state, owners, acceptance criteria, and dependencies are owned by ADO work items. The context only needs the stable project background plus how to find those work items — do not copy in a local task list that goes stale.

A link is not necessarily something the agent can open. For permission-gated Figma files, PM documents, or meeting notes, keep the essential summary, screenshot, or export in the context itself, and record the original source and the date it was captured.

### Let AI draft the first version

A prompt to start from:

```text
Read the code related to <project> and create a project context.

Start by summarizing:
1. project goals and user scenarios;
2. the main directories, components, and their responsibilities;
3. key data flows and dependencies;
4. how to build, test, and validate locally;
5. anything that cannot currently be confirmed from the code.

Do not guess business facts. List anything unconfirmed under Open Questions, and
attach a code path to every conclusion.
```

Then fill in the PM spec, developer design, Figma, and team decisions over time. Context deserves review the same way code does, and it should keep changing as the project evolves rather than being generated once and abandoned.

## 3. Set up cross-session memory

Context alone is not enough. Every new session has to know it exists and read it before discussing or changing the project.

Add one short, stable global instruction. Its only job is routing the agent to the source of truth — do not copy the project knowledge itself into memory:

```markdown
## <project> context

Whenever a request discusses <project>:
1. Read <context repository or directory>/README.md first.
2. Follow its reading order and treat the referenced project context as the source of truth.
3. Check status.md and the referenced ADO work items before planning changes so you account for current state and work completed by other contributors.
4. If the request conflicts with the context, surface the conflict instead of silently choosing one.
5. After discovering durable new project knowledge, update the appropriate context document.
```

### Why dotfiles is the right home for this

Say it out loud in a single session and the rule dies with that session. Configure it in one Codespace and you get to configure it again in the next one.

Putting the instruction in a personal dotfiles repository gives every Codespace the same project entry point automatically:

- Copilot CLI: `$HOME/.copilot/copilot-instructions.md`, or `$HOME/.copilot/instructions/*.instructions.md`
- Claude Code: dotfiles can install the same rule into the personal-level `CLAUDE.md`

For how to create and configure personal dotfiles, see the ODSP-Web wiki: [Using dotfiles for personal customization](https://dev.azure.com/onedrive/ODSP-Web/_wiki/wikis/ODSP-Web.wiki/141505/Using-dotfiles-for-personal-customization).

Keep one copy of the project instruction in dotfiles and let the install script copy or link it into each CLI's personal instruction directory. The context itself still lives in its own repository or in odsp-web; memory holds only the entry path and the reading rule.

This matters most with several people working together:

- every session starts from the same background;
- the agent can see what others have already finished before it writes code;
- new members come up to speed without relying on word of mouth;
- the context's Git history records how project knowledge changed.

Personal memory is only for stable "where to read" rules. Shared architecture, status, and decisions must stay in the project context — they cannot live only in one person's dotfiles.

## 4. Install agentOW

### Claude Code

```bash
claude plugin marketplace add kaixun96/dev.AgentOW
claude plugin install agentOW@agentOW
```

The Claude version additionally needs Agent Teams enabled and auto-accept turned on before running. See the project [README](../README.md#prerequisites) for the full prerequisites.

### Copilot CLI

```bash
copilot plugin marketplace add kaixun96/dev.AgentOW
copilot plugin install agentow-copilot@agentOW
```

The first agentOW run in a given Claude/Copilot terminal session starts with an automatic bootstrap:

- installs any missing Playwright, ODSP baseline MCP, and review plugins from the local trusted marketplace;
- installs opt-in MCPs when the task references Figma, ADO, Bluebird, wiki, or Learn;
- installs screenshot composition and pixel-diff dependencies for UI tasks;
- completes the Agent Teams setup on Claude;
- installs the Azure DevOps extension when the Azure CLI is already present.

New plugins and Agent Teams settings only load after Claude/Copilot or the terminal restarts. Bootstrap stops before planning and says so explicitly. Sign-in, Figma OAuth, AAD consent, the first Playwright login, and tenant fixtures still need you. Results are saved to `.aero/<session>/capabilities.json`, so later runs in the same terminal session do not reinstall.

### Recommended: run `ow-init` first

After installing agentOW, run a full initialization once before your first product task.

In an interactive Claude Code or Copilot CLI session, type:

```text
/ow-init
```

`ow-init` checks and installs the baseline MCPs, the Figma/ADO opt-in MCPs, and the UI image dependencies in one pass, without entering planning or touching product code. If the output asks for a restart, restart that CLI before running agentOW. Later, when something goes missing or breaks, use `/ow-doctor` to force a diagnosis and repair.

If Azure is not signed in, initialization tells you to run this in the **current Codespace terminal**:

```bash
CODESPACES=false az login
```

Re-run `/ow-init` once that finishes.

## 5. Choose a run mode

| Situation | Claude Code | Copilot CLI | Interaction |
|---|---|---|---|
| Single task, requirements and plan need confirming | `/ow-team` | `/agentow` | yes |
| Single task, context is already sufficient | `/ow-team --auto` | `/agentow --auto` | none |
| Runnable proof of concept, quality gates deferred | n/a | `/agentow --poc` | optional |
| Several independent tasks | `/ow-batch` | `/ow-batch` | none after launch |

### Interactive: for filling context gaps

When the requirement is still ambiguous, the design is undecided, or you are handling this kind of task for the first time, start interactive:

```text
/agentow
Implement the PhotoGrid loading state per project-context/product-spec.md.
```

Write the stable conclusions from that conversation back into the context. Interactive mode is not only about finishing the task — it is how you make later Auto and Batch runs reliable.

### Auto: single task once context is sufficient

```text
/agentow --auto
Read ADO work item 1234567 and complete it per its description and acceptance criteria.
```

Auto mode never waits for requirement clarification or plan approval. The agent records the assumptions it had to make into the run artifacts, so the task description has to point at a definite spec and definite acceptance criteria.

### POC: fastest path to a runnable result

```text
/agentow --poc --auto
Build a working prototype of the new PhotoGrid interaction so I can inspect the final result.
```

POC is an execution profile, while `--auto` controls interaction; use either `/agentow --poc` or
`/agentow --poc --auto`. POC keeps build/typecheck and final-result validation, but uses a bounded
main-session plan, skips tests by default, captures only an AFTER screenshot of the
requested/default UI state, and treats review as advisory except for Critical safety defects.

The output is always a `[POC]` draft PR with a **NOT PRODUCTION READY** warning and an explicit list
of skipped gates. agentOW never merges it. POC mode is not available for authentication/security,
privacy boundaries, destructive data operations, schema/data migrations, production configuration,
or secrets.

To turn the prototype into normal production work, reply in the same run:

```text
promote this POC
```

agentOW reuses the same `.aero` session, branch, and PR, then runs FULL planning, tests, complete
scenario BEFORE/AFTER validation, strict review, and context maintenance. It removes the POC warning
only after those gates pass.

### Automatic planner mode

For each Copilot `/agentow` task, agentOW automatically chooses `FAST` or
`FULL` planning. `FAST` is limited to bugs whose prompt supplies a complete
root-cause packet (symptom, code anchor, cause, intended fix, and verification)
that a bounded source read confirms, with one behavior and at most two product
files. Features, exploratory bugs, cross-package changes, mandatory context
audits, and unclear UI ownership use `FULL`.

`FAST` skips only the planner subagent. It still writes a source-cited planner
report and keeps the normal build, test, evaluator, screenshot, review, and PR
gates. Contradictory evidence or scope growth automatically escalates the run to
`FULL`. The decision and reason are visible in `progress.log`, `report.json`,
and `planning/planner-mode.json`.

### Batch: many independent tasks

```text
/ow-batch
Read every active bug in this ADO query and work through them one by one:
<ADO query URL>
```

Or list them directly:

```text
/ow-batch
Work through these ADO work items in order:
1234567
1234568
1234569
```

agentOW should pull each work item's current description, discussion, acceptance criteria, and links from ADO before generating the batch. Every item in a batch must be independently verifiable and independently shippable as its own PR. Do not disguise a chain of dependent steps as independent tasks — that work belongs in a single spec, or needs its dependency order stated.

## 6. Verification and run artifacts

The goal of agentOW is not "generate code" — it is "produce a reviewable result". A complete run keeps the plan, the implementation record, the evaluation, the review, and the final state.

For visible UI changes, Playwright BEFORE/AFTER screenshots are a mandatory gate. When the evaluator cannot open the page, authenticate, locate the element, or actually write the screenshot files, it must report the failure — it may never claim visual verification passed without screenshot evidence.

Progress and artifacts live in:

```text
/workspaces/odsp-web/.aero/<session>/
```

The ones worth reading:

- `progress.log` — live status;
- `plan.md` — plan, assumptions, acceptance criteria;
- `evaluation/` — verification reports and screenshots;
- `review.md` — code review results;
- `final.md` — final state and PR.

Batch runs also produce `summary.md` plus a separate log per task.

## 7. A working daily loop

1. Create or update the spec, design, and ADO work item entry points in the context.
2. Confirm memory lets a new session find the context on its own.
3. Use interactive mode the first time you touch a new area.
4. Write the stable knowledge from that conversation back into the context.
5. Use Auto once the task and its acceptance criteria are unambiguous.
6. Use Batch when several tasks are genuinely independent.
7. Review the draft PR, the screenshots, and the run artifacts.
8. Keep writing wrong assumptions, missed constraints, and new decisions back into the context.

The point of this loop is not longer and longer prompts — it is a source of truth that keeps getting more accurate. agentOW executes the process reliably; the project context decides whether it is solving the right problem.
